## Skillware POIs keep their identity

The User noticed that a Skillware POI's situation carried `surface_state`, the
content hashes of every file of its skill package. Because a POI's identity
is its Type and situation, any edit to the package gave every open Skillware
problem a new identity: the action store held 116 actions for 43 problems,
110 of them closed as gone. A first fix moved the state into the details and
let a blessing "pin" it; the User rejected that. A blessing accepts a
situation, and the situation names every fact relevant to the check; when
one changes, the check raises a different POI and the blessing does not cover
it. Details are only what an Agent may find useful, possibly nothing. So the
package state is gone from Skillware POIs entirely, and there is no pinning.
An audit for the same principle found the System Project's active-Project
check naming Projects by absolute path (now by UUID; a missing Project by its
active path). The User had the 1018 action records with dead identities
deleted: the 116 that carried `surface_state` and 902 naming Projects by
absolute path from before Project UUIDs. Request 925.

## Situation Chains

Discussing the blessing model, the User set it inside one chain:
Situation → Check → POI → Action → Closing, a Situation Chain, modeled as one
class grouping the Types of its links. Checks become atomic and built with
the situation their caller creates; Suites find situations and run them;
every POI Type gets its own Action Type; external tools follow the Gitleaks
template (native run, stored report, situations found in it). Captured in
[situation-chains](../situation-chains.md); implementation request 926 waits
for alignment on three questions.
